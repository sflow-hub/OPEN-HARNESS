# Security

## Trust model

Open Harness is built for a single trusted operator, or a small trusted team, self-hosting on infrastructure they control. It is not multi-tenant and provides no isolation between different human operators of the same coordinator. Anyone who can reach the coordinator's port, or who can run code as the OS user running the coordinator or a runner, has full operator-level access: they can create runs, read and write every agent's private files, and read stored model credentials.

The dashboard bootstrap token (served from `/v1/bootstrap`) is the clearest expression of this: it authorizes arbitrary run creation, host-path container mounts, and direct OS-account execution. It is served only to callers presenting a loopback `Host` header, specifically because a same-origin check alone cannot distinguish a local browser from a DNS-rebinding attacker. Setting `OPEN_HARNESS_ALLOW_REMOTE_DASHBOARD=1` disables that check; it is a deliberate, opt-in trust decision for operators who put their own authenticated reverse proxy in front of the dashboard, not a bug if you encounter it enabled.

## Isolation boundaries

**Per-agent containers** (the default): each agent runs in its own Docker container. The host home directory, the Docker socket, and other agents' private directories are not mounted into it. The container is the filesystem boundary; Hermes's own execution guards apply inside it. Filesystem isolation and process-tree termination on stop are part of the security surface we care most about getting right — if you find a way to escape a container or to leave orphaned processes running after a stop, that's a security bug, not just a correctness bug.

**Selected folders**: mounts only the host folders an operator names into the container, honoring the read-only/read-write setting chosen for each. A folder mounted read-write is fully writable by that agent.

**Direct computer access**: runs Hermes directly under the runner's OS account, with no container boundary at all. This is an explicit, opt-in trade of isolation for host-native capability (screen, accessibility APIs, an existing desktop session). Anything reachable by the OS account running the runner is reachable by the agent. Treat a runner configured this way as fully trusted, equivalent to giving the agent a shell as that user.

**The self-hosted Docker Compose stack** (`compose.yaml`) runs a `docker:*-dind` sidecar with `privileged: true` and no TLS (`DOCKER_TLS_CERTDIR: ""`), reachable only from the `open-harness` coordinator container over the compose-internal network. That coordinator container is therefore equivalent to root on the host it runs on. Do not add other services to that compose network, and do not expose the `docker` service's port beyond it.

## Operator controls and audit

- **Audit trail.** A selected set of actions is recorded to an append-only `audit_events` table (`runtime/audit.ts`). What is emitted today, all with actor `operator`: agent create/delete and profile saves, credential create/rotate/update/delete, workspace model-default changes, direct-access enable/disable, conversation changes, and machine reconnect/revoke; plus runner pairing with actor `runner`. The schema's `actor_kind` CHECK also permits `agent` and `system`, but no code path emits those kinds yet, and nothing records ordinary agent or system activity. Database triggers reject every update and delete, secret-like fields are redacted, and `detail` is capped at 4 KB. The log is read over `GET /v1/audit` (cursor plus `action`/`targetKind`/`targetId` filters); it requires the operator control token and is not reachable with an agent's `/internal/*` token.
- **Direct computer access** is off by default. The operator must enable it in Workspace settings → Security and confirm that it gives the agent a shell on that computer; the change is audited. Saving a `direct` profile or starting a direct run while the gate is off is refused. Paired runners also require the local opt-in environment variable `OPEN_HARNESS_ALLOW_DIRECT=1`. Disabling the workspace gate blocks new direct runs and profile saves; existing profiles can be switched to isolated access.
- **Per-agent network policy** is a stored setting only (`NetworkPolicy` in `lib/agent-profile.ts`, default `open`). It is **not yet enforced** — containers still launch with open egress and no `--network` restriction — so it makes no isolation promise today. See [`docs/design/agent-network-policy.md`](docs/design/agent-network-policy.md).
- **Per-team shared folders.** Each team gets `${stateRoot}/teams/<teamId>/shared`, mounted into member agents at `/workspace/teams/<teamId>` (`runtime/hermes.ts`); an agent in no team gets no team mount. These mounts reflect membership only at the moment a container is created or reconciled. The team set is part of `containerSignature`, but the resulting rebuild is gated on the agent being idle (`shouldRebuildContainer`, `runtime/hermes.ts:298`) and the per-agent gateway is cached and reused (`gatewayFor`, `runtime/service.ts:235`), so removing an agent from a team does **not** immediately revoke its filesystem access — a busy container keeps the old mounts until it next rebuilds while idle. This is additive: the legacy global `/workspace/shared` is unchanged and stays read-write for every agent, so it remains a cross-agent read-write channel.
- **Revoking a paired computer.** The Computers page lists paired computers. Revoking one — not permitted for the local computer — invalidates that runner's credential, cancels its queued runner commands, and fails any run active on it with `Computer was revoked.`; new enqueues to a revoked machine are then refused. The action is audited (`machine.revoke`).
- **Approvals API.** `GET /v1/approvals` is operator-only and returns a `pendingCount`. Each summary is assembled from an allowlist of fields with inline secret masking, so no unexpected field reaches the browser. A pending approval whose run has already reached a terminal state is reported as `expired`, and resolving it returns `409`. (The inbox UI is not merged yet.)
- **Sandbox self-test.** `POST`/`GET /v1/agents/:id/sandbox-selftest` check an agent's isolation. Host-attested `docker inspect` facts are authoritative; the in-container probe only corroborates and a contradiction is reported as tampering. Paired runners are labelled `runner-attested` (lower trust) and direct access reports `not a sandbox`. Results are stored and audited (`sandbox.selftest`). Real-container verification is still pending, so this is not yet a production isolation claim — see [`docs/design/agent-network-policy.md`](docs/design/agent-network-policy.md).
- **Agent-directory file safety (Linux).** An agent's containers mount `private`, `profile`, and `shared` read-write, so an agent can plant or race a symlink and wait for the operator to drive a coordinator file endpoint through it. On Linux the coordinator defends against this: every path operation is resolved from a trusted coordinator-owned anchor — `${stateRoot}` and `${stateRoot}/agents/<id>`, which are never bind-mounted into a container — through held directory handles (fd-relative via `/proc/self/fd`, `O_NOFOLLOW`), so each component is openat-relative to a held inode and a planted or racing symlink cannot redirect a read, write, or delete outside the agent or shared directories (`runtime/safe-fs.ts`). This covers `/v1/files` (read, list, write, delete), the skill and context (`MEMORY.md`/`USER.md`) endpoints, the `/v1/migrate` profile and shared writes, and agent file transfer export/import (`runtime/transfer-files.ts`). A `DELETE` of a symlink is refused rather than followed. That refusal is a check-then-unlink on Linux too, for both a single-file `DELETE` and the recursive delete: a concurrent replacement landing between the `lstat` and the `unlink` can remove the replacement name (for example a just-planted link itself) through the held parent directory, never its outside target. Hard links are allowed: a hard link an agent creates to a file elsewhere on the same filesystem is read and written as an ordinary file, because a hard link is another name for the same inode, not a traversal out of the directory. `/v1/bootstrap` reports the active mode as `fileSafety` (`fd-relative` | `path-fallback` | `unsupported`). Test-only race hooks exist only behind `OPEN_HARNESS_SAFE_FS_TEST_HOOKS=1` and are off by default. See [`docs/design/file-safety.md`](docs/design/file-safety.md) for the design and the fallback's limits.

## Known limitations

Current, factual gaps on this development branch:

- **Agent-directory file safety is Linux-only; other hosts keep the legacy pathname behaviour.** macOS and Windows hosts use the path-fallback, which provides lexical containment only and remains exposed to the parent-swap race (a running agent swapping a parent directory between the check and the use). A failed Linux capability probe selects `unsupported`; file operations fail closed with HTTP 400. Avoid the file, skill, context, and transfer endpoints on agents you do not trust there. Two fallback-only sharp edges: the recursive skill `DELETE` walks post-order with no pre-scan, so it can remove earlier files before it reaches a nested symlink and stops; and fallback writes use a plain pathname write that can hang on a FIFO an agent planted at the target.
- **A narrow residual window remains in the Linux recursive delete.** Inside a directory it already holds by fd, each entry is `lstat`-ed and then unlinked through that held handle; a swap landing between the two acts on whatever name now exists in the held directory and unlinks it as a link rather than following it, so the worst case is removing an entry inside the held directory, never one outside it (`removeTree`, `runtime/safe-fs.ts`).
- **safe-fs has not been exercised on every supported configuration.** It is untested on Node 22.13 (the `engines` minimum in `package.json`; the suite ran on Node 24) and inside the coordinator container. Real-Docker validation is still pending (no VM has been approved), as are an agent file transfer over a real paired runner and the macOS/Windows path-fallback.
- **Multi-file transfer imports are not all-or-nothing.** Files are committed one at a time, so a failure part-way leaves earlier files in place; the error reports how many of the bundle's files were committed (`runtime/transfer-files.ts`).
- **A failed Linux capability probe fails closed.** When the fd-relative probe does not pass, `requireMode` throws and the request returns HTTP 400 rather than a 5xx, so a host without working `/proc`-based access refuses file operations instead of silently degrading.
- **Context and skill reads are not size-capped (pre-existing).** `/v1/files` reads cap at 1 MB, but the skill `GET` and the `MEMORY.md`/`USER.md` context reads pass no byte limit, so a large agent-written file is read whole into coordinator memory.
- **Minor, filed for follow-up.** A first concurrent use of a file scope can return `409`, because `ensureFileDir` does a non-atomic stat-then-mkdir. File listing reads the whole directory and re-`stat`s every entry (an N+1) before trimming to 200 results. An agent filename containing a backslash fails the entire transfer export rather than skipping that one file. Synchronous filesystem work runs on the event loop. Linux recursive deletion and transfer export enforce entry/depth limits, but fallback recursive deletion does not; listings read the whole directory before trimming results.
- **Finished runner commands are scrubbed, but a few failed ones only on restart.** A completed or failed command drops the credential material and probe input it carried (`spentPayload`, `runtime/machines.ts`). Commands failed by a machine revoke or by lease reconciliation keep their payload until the next coordinator restart, whose startup sweep rescans all finished rows and scrubs them.
- **Per-agent network egress is not enforced.** Network policy is a stored setting only; containers still launch with open egress and no `--network` restriction. See [`docs/design/agent-network-policy.md`](docs/design/agent-network-policy.md).

## The Hermes pin

Open Harness vendors a specific pinned commit of [Hermes Agent](https://github.com/NousResearch/hermes-agent) (currently recorded in [`runtime/hermes/NOTICE.md`](runtime/hermes/NOTICE.md)) into its own container build, and does not modify Hermes's reasoning loop. A vulnerability in Hermes itself, independent of how Open Harness integrates it, should also be reported upstream to Nous Research. We aim to bump the pin promptly once a fix lands upstream; a report here that turns out to be purely a Hermes issue will still get triaged and forwarded, not dropped.

## Reporting a vulnerability

Please report suspected vulnerabilities privately through [GitHub Security Advisories](https://github.com/sflow-hub/OPEN-HARNESS/security/advisories/new) for this repository, rather than as a public issue. We'll acknowledge receipt and work with you on a fix and disclosure timeline before any public detail is published.

**In scope**: authentication/authorization bypass (including anything that defeats the loopback bootstrap check without the documented opt-out), container escape or filesystem-isolation failures in the default per-agent-container mode, incomplete process-tree termination that leaves agent-spawned processes running after a stop, secret or credential leakage (including via logs, exports, or the Docker build context), and cross-run or cross-agent event forgery (a paired runner or agent affecting a run or agent it shouldn't be able to reach).

**Out of scope**: behavior that only follows from an operator having deliberately enabled a documented escape hatch (`OPEN_HARNESS_ALLOW_REMOTE_DASHBOARD=1`, Direct Computer Access, a read-write Selected Folder), and the absence of multi-tenant isolation, since none is claimed.

## Supported versions

Open Harness is pre-1.0. We patch `main` and the latest tagged release; older tags are not backported.
