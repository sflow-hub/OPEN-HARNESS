# Agent coordination — Claude and Codex on the Open Harness MVP

Two agents work on this tree at the same time from two different places. This file is
the only handoff channel between them. Read it before every edit; update it after every
delivery. It is not user documentation and is not shipped anywhere.

## Protocol

1. **Ownership.** Each agent lists the files it owns below. Only the owner edits an owned
   file. To change a file the other agent owns, write what you need under **Requests** and
   wait for the owner to make the change (or explicitly hand the file over in the log).
2. **This file.** Edit only your own section, plus appends to **Log** and **Requests**.
   Never rewrite the other agent's section.
3. **Shared files** (`package.json`, `package-lock.json`, `CHANGELOG.md`, `README.md`,
   `ROADMAP.md`, `CLAUDE.md`, `AGENTS.md`): announce in the log *before* editing, keep the
   edit to your own bullets or a clearly separated block, and re-read the file right before
   writing it. `CHANGELOG.md` `[Unreleased]` gets one bullet per user-visible change; sign
   the bullet with `(claude)` or `(codex)` at the end so overlap is visible.
4. **Re-read before write.** The shared folder has no git, so the disk is the truth. Read a
   file immediately before writing it; if it changed since you last read it, merge, don't
   overwrite. Claude's delivery tool refuses a write when the file on disk changed after
   Claude last read it, and reports the collision here instead of forcing.
5. **Verification.** Whoever changes code runs the checks that cover it (`npm test`,
   `npm run typecheck`, `npm run lint`, `npm run build`; `npm run test:browser` for
   `components/` or `app/` changes) and records the result in the log entry.
6. **Log entries** are one line each, newest last: `YYYY-MM-DD HH:MM MDT — agent — what
   changed, which files, which checks passed`.

*Requirements a sandboxed direct mode must meet (security).*
1. OS-enforced, not policy-enforced: kernel/OS mechanisms that a child process cannot switch off —
   Linux: mount + user + PID namespaces via bubblewrap with `no_new_privs` and a seccomp filter, or
   Landlock (kernel ≥ 5.13, inherited and irrevocable) as the no-namespace fallback; macOS: a Seatbelt
   profile via `sandbox-exec` (what Chrome, Bazel, Codex CLI and Claude Code use there; deprecated API,
   still shipped); Windows: nothing per-process without a second account/AppContainer, so **unsupported
   → fail closed**. A renamed or re-parented python, an allow-list of tools, or a policy file is not a
   sandbox and must never be labelled one.
2. Filesystem default-deny. Readable: the OS and the Hermes/python installation (read-only). Read/write:
   the agent's `profile/` (as `HOME`), `private/`, the workspace `shared/` (shared by the user's
   choice), each selected folder with its own read/write mode, a private `tmp`. Denied by omission:
   the operator's home and everything in it (`~/.ssh`, keychains/vaults, browser profiles, shell rc),
   the state root above the agent's own directories (`state.db`, `secrets.json`, `agents/<other>/`),
   the runner's credential files, the Open Harness checkout except the files the entry needs. Links
   planted in a granted directory must resolve inside the sandbox's own view (bind mounts and Landlock
   both do this at the kernel; the container-side `sharedFolderSource` checks stay).
3. No inherited environment. The child gets an explicit allow-list only: `PATH` (curated), `HOME` =
   profile home, `TMPDIR`, `LANG/LC_ALL/TZ`, `HERMES_HOME`, `HERMES_TUI`, `HERMES_GATEWAY_SESSION`,
   `PYTHONUNBUFFERED`, `OPEN_HARNESS_POLICY_PATH`, `OPEN_HARNESS_CONTROL_SOCKET`, and `DISPLAY` /
   `WAYLAND_DISPLAY` / `XAUTHORITY` / `XDG_RUNTIME_DIR` only when a desktop is configured. Nothing
   else from `process.env` — today it carries whatever `.env` the coordinator loaded, including
   provider keys and `OPEN_HARNESS_*` values. Model/connector credentials keep arriving through the
   profile `.env` the agent already owns.
4. Coordinator and runner credentials unreachable: the credential store, the bootstrap token, the
   runner pairing credentials and other agents' `.env` files are outside the allow-list; the agent
   keeps only its run-scoped token over the coordination socket (`agentToken`, already scoped).
5. Applies to every descendant and to discovery: the wrapper is the root of the process tree, so
   terminal commands, `execute_code`, browsers and MCP connector processes inherit it (namespaces,
   Landlock and Seatbelt all inherit; `no_new_privs` closes setuid). The catalog, computer, model and
   MCP probes run under the same plan as a run. PID-namespace or `setsid` + the wrapper's identity give
   recovery a single tree to stop.
6. Fail closed: a profile that requires the sandbox never starts unsandboxed. No bubblewrap, no user
   namespaces, no `sandbox-exec`, Windows, a failed self-test → the run fails at admission with a
   specific reason, the probe reports the same reason, and nothing is executed on the host.
7. Truthful platform support: capability is a verified self-test on that machine (a canary process
   tries to read the state root and the home, checks its environment, spawns a child that must also
   be denied, and confirms `no_new_privs`), reported per machine, refreshed on heartbeat, and shown
   as-is. `verified: false` is displayed as unsandboxed, never as "sandbox enabled".
8. Resource limits are separate and optional (cgroups via `systemd-run --user` on Linux); the contract
   says whether they applied, the UI does not promise them.

*Design concerns, ranked.*
- **P0 — the operator token is one loopback GET away.** File sandboxing does not change that a
  host process, sandboxed or not, can `curl -H 'Host: localhost' http://127.0.0.1:4317/v1/bootstrap`,
  take the operator token and then create runs for any agent with any folder grant or unsandboxed
  direct access — a complete escape. The network cannot simply be removed (local model servers on
  127.0.0.1 are a supported configuration). Bootstrap must require something the sandbox cannot obtain:
  e.g. a dashboard secret in a 0600 file outside every allow-list that the Next proxy attaches for the
  browser (an unsandboxed same-user process reading that file is the existing trust model, unchanged),
  or a Unix socket with peer-credential checks. Without this the mode should not be called sandboxed.
  This is the `operator-api-denied` self-test check above.
- **Architectural — control of the operator's existing desktop is outside any process sandbox.**
  With `desktop: 'existing'` the agent drives the real session: it can open a terminal, a password
  manager or a browser with saved logins, and every command typed there runs as the user, outside the
  agent's process tree. No file or process sandbox contains this; the only containments are a separate
  desktop session (a second OS user, a nested Xvfb/Weston display started inside the sandbox on Linux,
  the existing container virtual desktop) or platform controls outside our reach on macOS/Windows.
  Proposal: existing-desktop control is only offered with the sandbox off and its acknowledgement, the
  copy says why, and a host-native private virtual desktop is a separate later feature. Calling the
  combination "sandboxed" would be false.
- Inherited environment and unsandboxed probes are the two current leaks that a first delivery must
  close together with the run path (requirements 3 and 5); the catalog probe runs on the host the
  moment Agent settings opens.
- Linux reality: Ubuntu 24.04 restricts unprivileged user namespaces through AppArmor; the packaged
  `bubblewrap` carries a profile and works, a hand-built one may not, hence the self-test rather than
  `which bwrap`. Landlock (Ubuntu 24.04's 6.8 kernel has ABI 4) is the fallback that needs no
  namespaces; it can be applied from a tiny Python launcher via `ctypes` before `exec`, so no native
  Node module is required. Both should be reported as distinct mechanisms.
- macOS: `sandbox-exec` is deprecated but still shipped in current macOS releases and relied on by
  widely used tools; treat it as best-effort with the self-test as the gate; TCC (Accessibility, Screen Recording)
  interacts badly with a deny-default profile, which is another reason existing-desktop stays out of
  the sandboxed mode.
- Windows: no honest per-process sandbox without a second account or AppContainer; ship
  `supported: false` and point at Private workspace (Docker Desktop) rather than approximate.
- Recovery: with a wrapper the saved PID is the wrapper's; `--unshare-pid --die-with-parent` (or
  `setsid`) makes stopping the wrapper stop everything, and `recoverNativeProcess` should be exercised
  with the wrapper in place.
- Migration: existing `direct` profiles cannot silently become `required` (their hosts may lack the
  sandbox and every run would refuse) nor silently stay `off` (nothing would change for them). Proposal:
  they load as `off`, the Computer tab and the agent card show the unsandboxed badge, and one notice
  asks the operator to choose. User's call.
- Not covered by this design, and should stay documented as such: outbound networking and reachable
  host services (unchanged by the user's choice), `shared/` being shared, and macOS/Windows Docker.

*Response to Codex's sandbox-runtime update (relayed 12:10 MDT), added 12:20 MDT.*
`@anthropic-ai/sandbox-runtime` (bubblewrap + seccomp on Linux, Seatbelt on macOS, deny-read root
with explicit allow-lists, sanitized environment, all traffic through host-side filtering proxies,
Unix-socket allow-list) is the same machinery Claude Code ships, and it covers requirements 1–6 above
directly; the proxy layer answers the P0 by making the coordinator port and other local services
unreachable from inside rather than by trusting the file layer. Keep the following as self-test items
rather than assumptions, because each is where that design leaks in practice: (a) if the local model
server is allow-listed by host (`127.0.0.1` for Ollama/LM Studio), the rule must be port-aware or use a
dedicated hostname, or the coordinator port comes back with it — `operator-api-denied` must be tested
*with* a local model host allow-listed; (b) inside the sandbox only proxy-aware clients have network:
Hermes's Python HTTP stack honours `HTTP(S)_PROXY`, the browser tool's Chromium needs an explicit
`--proxy-server`, and Node's `fetch` ignores proxy variables — so `coordination.mjs` must keep using
the Unix socket, and the browser tool needs a check or an honest "no network in the browser tool under
the host sandbox"; (c) the coordination socket path and the profile/private/shared/grant paths are the
only writable allow-list, `managed/` read-only, everything under the state root otherwise unlisted;
(d) the catalog/computer/model probes go through the same wrapper as a run (today they are the
unsandboxed path that runs first).

**Ubuntu 24.04 and the netns block — do not weaken the system, but do not ship a fallback that
silently drops the network layer either.** Two scoped options that are not system-wide changes:
a per-executable AppArmor profile that grants user namespaces to `bwrap` alone (what Ubuntu itself
ships for its own bubblewrap/Flatpak users), installed by `harness:setup` only with an explicit
sudo prompt and documented; and, independently, hardening `/v1/bootstrap` server-side (a 0600
dashboard secret outside every allow-list, attached by the Next proxy) so a files-only tier is not
an operator-token escape. With both, the contract can honestly offer two host tiers and name them:
`host: files+network` (bubblewrap + proxies, verified) and `host: files only` (Landlock or bwrap
without netns, bootstrap hardened) — the UI shows which one ran, never just "sandboxed". If Codex
prefers a single tier, fail closed on stock Ubuntu 24.04 and say so in readiness; that is the
supported beta platform, so the install path should then carry the AppArmor step.

**A simpler architecture (asked for).** Treat the host sandbox as a second *isolation engine* for the
access levels that already exist, not as a variant of Direct. The user already chooses *what* an
agent may touch — Private workspace (own files + shared), Selected folders (plus named host folders,
read or write), Direct (everything the account can). The runtime chooses *how* that is enforced on
the selected machine: Docker container when the image is ready, else the verified host sandbox with
the same inputs (private dir, shared, grants → bind list), else fail closed. Consequences: no new
per-agent security switch and no `sandbox` field on `ComputerConfig` (an optional
`engine: 'auto' | 'container' | 'host'` preference at most); no 2×2 of "direct × sandbox"; "sandboxed
direct with the existing desktop" cannot be expressed, so the contradiction disappears by
construction — `desktop: 'existing'` stays where it is today, on Direct, which stays unsandboxed and
is finally labelled so; `desktop: 'virtual'` requires the container engine; existing `direct` profiles
need no migration; existing `private`/`folders` profiles gain nothing and lose nothing. What it adds
is real: a Docker-free Private workspace and Selected folders on macOS and Linux machines with a
verified host sandbox, which is where `sandbox-runtime` is strongest. Contract deltas versus the
proposal above: `MachineInfo.capabilities.sandbox` as specified; `ComputerConfig` unchanged (or the
optional `engine`); `validateComputerTarget` accepts `private`/`folders` when either engine is
verified; runs, probes and `run.started` carry
`isolation: { engine: 'container' | 'host' | 'none'; mechanism: 'docker' | 'bubblewrap' | 'landlock'
| 'seatbelt' | 'none'; network: 'filtered' | 'host'; verified: boolean }`; the `Test access` checklist
is the host engine's self-test; readiness gains `host-sandbox`. UI under this shape: the access
radios stay as they are, Direct's copy becomes "Unsandboxed — everything your account can reach" with
the acknowledgement checkbox, the machine card states the engines ("Container: ready · Host sandbox:
bubblewrap, network filtered, verified 12:04"), an engine preference appears only when both are
available, and every run shows its `isolation` as a badge. This is the shape I recommend; the field
proposal above stands if Codex wants a per-agent switch instead.
