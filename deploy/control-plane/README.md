# Provider-neutral control plane

The coordinator remains a private workspace service. This deployment adds accounts, human membership, signed relay identity, usage/billing metadata, and lifecycle jobs in PostgreSQL. It does not provision shared agent hosts. Managed workspaces require a dedicated Linux VM per workspace through the selected `WorkspaceProvider` adapter. No production adapter is selected in this checkout.

Copy `config.example.json` to `config.json`, choose the public and identity domains, and supply a confidential OIDC client secret through the named environment variable. Generate a persistent Ed25519 private JWK and keep it in `secrets/relay-private.jwk`, mode `0600`. Only its public JWK goes to workspace computers. The Keycloak reference realm disables public registration and password grants and requires PKCE and verified email. Configure SMTP and invite test accounts through the realm administrator. Use a separate PostgreSQL schema or database and database role for Keycloak in production; the reference schema needs to exist before realm startup.

Run `npm run cloud:serve` with `DATABASE_URL` and `OPEN_HARNESS_CLOUD_CONFIG`. Development HTTP is allowed only for loopback identity/public endpoints with `OPEN_HARNESS_DEVELOPMENT=1`. Production uses authenticated HTTPS. The Compose reference requires explicitly reviewed image digests and keeps PostgreSQL and the HTTP control service off public host ports. Build the dashboard with `NEXT_PUBLIC_OPEN_HARNESS_CLOUD=1`; route its cloud/API/WebSocket paths to the control service as shown by the Caddy configuration. Configure actual backups, health monitoring, and all release gates before exposing it.

Each model configuration has `id`, `upstreamModel`, a fixed HTTPS `endpoint`, `apiKeyEnv`, `enabled`, `maxOutputTokens`, and `rate: { version, inputMicrodollarsPerMillion, outputMicrodollarsPerMillion }`. Rates must be approved before enabling a model; the sample deliberately supplies none. New wallets have zero balance and a zero spending limit. Usage reserves a conservative text/tool bound before dispatch, reconciles provider usage once, and holds uncertain requests. Included multimedia and unsupported runner model leases return explicit errors. Model provider keys stay in this service. Existing user keys remain usable in self-hosted workspaces.

Billing configuration accepts server-defined `products` with `id`, `label`, `microdollars` and optional `stripePriceId`, `appleProductId`, and `googleProductId`. Configure `stripeKeyEnv` and `stripeWebhookSecretEnv` for web checkout. Apple configuration requires `bundleId`, the production `appAppleId`, and reviewed DER `rootCertificateFiles`. Google configuration requires `packageName` and a private `serviceAccountFile`. Webhooks are `/billing/stripe/events` and `/billing/apple/events`; Google refund checks use its verified voided-purchases API. Test receipts cannot fund production wallets. Credits, holds, charges, refunds and entitlements share one ledger; automatic recharge stays off. Refunds freeze new spending until the adjustment is reconciled.

For a self-hosted server using remote human roles, create a self-hosted workspace, mint its owner-only relay credential, and configure the server with its workspace ID, `OPEN_HARNESS_REQUIRE_RELAY_IDENTITY=1`, `OPEN_HARNESS_RELAY_ISSUER`, `OPEN_HARNESS_RELAY_PUBLIC_JWK`, `OPEN_HARNESS_CONNECTION_CALLBACK=https://YOUR_DOMAIN/connections/callback`, and the relay URL/token. Run `npm run workspace:relay`. Keep the coordinator loopback-only. Membership renewals run independently of browsers; expired renewal stops new standing work and credentialed actions. The browser receives server sessions, never the coordinator operator token. Native clients exchange system-browser authorization codes and store rotating scoped session tokens in the OS secure store.

Google/GitHub app registrations, Gmail scope verification, push credentials, model rates, signing, store billing and live acceptance are deployment inputs. Personal app credentials live in a dedicated workspace vault and require explicit agent sharing. Managed/shared authenticated workspaces may not use host-folder grants to expose the coordinator’s private state. A production provider must be explicitly named by `OPEN_HARNESS_PRODUCTION_PROVIDER`; its module must implement all seven lifecycle methods and pass real isolation/lifecycle acceptance before declaring `productionAccepted`.

The nine reference workflows, failure injection, physical-device checks, encrypted restoration, operational runbooks and latency evidence remain separate release requirements. A passing UI or scripted-provider test is not model-quality or production-isolation evidence.

The self-hosted coordinator image now fronts its internal dashboard with a small HTTP/desktop-upgrade proxy. It forwards only the one-use desktop stream path to the loopback coordinator; other upgrades are refused. Normal traffic continues to use the authenticated dashboard API proxy. OAuth authorization through that proxy derives a registered callback on the public dashboard origin; set `OPEN_HARNESS_CONNECTION_CALLBACK` explicitly for cloud relays and custom reverse proxies. Remote streaming requires the configured HTTPS `OPEN_HARNESS_DESKTOP_ORIGIN` (local loopback origins remain supported).

The GitHub connection uses the registered GitHub App’s user authorization/PKCE flow and expiring user tokens. Configure its repository/account permissions during registration; the broker’s separate read/write authorization and exact write approvals still apply. Token refresh requirements are described in the [GitHub user-token documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app). Provider registration and live read/write/revocation acceptance remain launch gates.
