# Operations and incident procedures

This is a deployment candidate, not an accepted service. Public managed provisioning stays disabled until a production provider is selected and its adapter is accepted against real dedicated Linux VMs. Configure identities, scopes, model rates, domains/TLS, billing, push, signing and backup credentials explicitly; do not expose the private coordinator port.

## Preparation and capacity

Build `Dockerfile.control-plane` and `Dockerfile.cloud-dashboard` with an explicitly reviewed digest-pinned `NODE_IMAGE` (Node 22.13+), scan both images and their dependencies, and record their immutable IDs. The cloud dashboard is compiled with `NEXT_PUBLIC_OPEN_HARNESS_CLOUD=1`. Use reviewed PostgreSQL/Keycloak/Caddy image digests in the Compose reference. A fresh reference PostgreSQL volume initializes Keycloak’s schema; existing deployments must create that schema separately. Use separate least-privilege database roles for identity and control data in production. Back up PostgreSQL before upgrades and apply schema changes in a controlled maintenance window.

The coordinator enforces one task per agent, two human-started tasks and four total including delegation. Interactive assistant tasks receive reserved admission capacity. Prewarming is opt-in, limited to one idle private runtime, expires after five minutes, and runs only after confirmed cleanup. Selected folders always receive fresh verification. Model reservations serialize on the wallet, enforce both balance and monthly hard limit, and allow at most four outstanding provider requests per workspace. Configure provider account VM quotas, per-account workspace quotas, control-service CPU/memory limits and alert thresholds in the accepted provider adapter. These provider capacity policies cannot be accepted before provider selection.

## Monitoring

Probe `/health/ready` for database/control readiness and each private coordinator’s bounded readiness API through an authenticated relay. A public probe exposes no credential or account data. Owners can inspect lifecycle jobs, held usage and audit metadata at `/cloud/v1/workspaces/ID/operations` and in Account. Workspace performance reports distinguish acknowledgement, queue, preparation, gateway readiness, first actual text, tools, intervention, cleanup and verified outcome. Monitor provisioning lease age/attempts, offline relays, failed backups, notification delivery failures, uncertain effects/usage, wallet holds and process cleanup. Do not treat provider output or task completion as a quality verdict. Establish external alerts and a documented on-call destination during deployment acceptance; none is provisioned by this checkout.

## Uncertain actions and usage

Never retry an uncertain external write as a new action identity. Connected actions have read-only reconciliation; unclassified shell/browser actions require a recorded human destination check. The affected task cannot automatically continue or repair while uncertainty remains. A human desktop lease belongs to its controller; another operator cannot send input. An owner can finish a redacted recording and release a stranded lease. Unconfirmed cleanup blocks the affected computer.

Provider usage holds are authoritative until actual provider usage is independently confirmed. A trusted service operator with direct database access can run `npm run cloud:operations -- reconcile EVIDENCE.json`, supplying `reservationId`, actual `inputTokens`, `outputTokens`, `providerReceipt` and a meaningful `evidence` reference. Set `DATABASE_URL` and `OPEN_HARNESS_OPERATOR_ID` in the protected shell. The command retains the source evidence file’s SHA256 in audit metadata and settles the reservation once; it does not estimate missing receipts. Preserve the provider’s original report privately. Refunds revoke the entitlement, preserve existing reservations and freeze new spending. After debt and all uncertain usage are reconciled, `npm run cloud:operations -- unfreeze EVIDENCE.json` accepts `workspaceId` and independent adjustment `evidence`. It refuses outstanding debt/unknown usage and leaves automatic recharge off. These commands are not exposed to workspace client sessions.

## Backup and restore

Owners enable encrypted daily backups with a 32-byte recovery key kept separately. Archives use AES-GCM plus per-file checksums. Configure S3-compatible storage with a dedicated workspace prefix and credentials scoped to that prefix; retain offline copies of recovery keys, PostgreSQL backups and relay signing keys. Defaults are raw events/backups 30 days, audit metadata 365 days, and user-controlled saved results. Owners may change retention. Current portable archive limits are 256 MB total, 10,000 files, 128 MB for SQLite and 16 MB per other file; larger deployments need a reviewed larger-workspace backup adapter before launch.

Restore into a new folder on a fresh host with `npm run harness -- restore --from BACKUP.ohb --to NEW_FOLDER`, supplying the key through `OPEN_HARNESS_BACKUP_KEY`. Credentials/browser sessions are omitted, runner pairings are revoked, and routines/responsibilities are paused. History and revisions are preserved; computer reassignment creates a new revision. Reauthorize accounts and model access, run a real setup task with file readback, inspect uncertain historical effects and resume reviewed routines individually. Exercise authenticated backup downloads and S3 readback during deployment acceptance.

## Incident and rollback

For suspected credential exposure, revoke membership/connections and stop affected tasks, rotate the relevant daemon/app/provider keys through their owners, and preserve restricted audit evidence. Keep the service loopback-only during investigation. Do not post suspected vulnerabilities to public issues. For a failed provider job, inspect its actual VM state, then retry the same job identity through the owner lifecycle API; the adapter must retain idempotency across restarts. Job heartbeats prevent ordinary long operations from losing their lease.

Stop new admissions and pause standing work before rollback. Keep database and encrypted-file snapshots from before the upgrade. SQLite refuses unsupported downgrades and takes a pre-upgrade backup; never point an older binary at a newer data format. Restore the matching previous application, database and file snapshots to a new host, verify actor/connection isolation and destination state, then cut over. Retain the failed deployment and evidence privately until recovery is accepted. Signed desktop rollback and native-store rollback need physical-platform acceptance, not just web tests.
